## Current Focus

**Phase 3 — LLM Integration.** Core agentic build complete, verified end-to-end over real HTTP.

**Final shape:**

```
main.py
  -> /chat: ChatRequest{session_id, message} -> ChatResponse{reply}     [conversational, always 200]
       -> graph.py: run() -> supervisor.invoke() against a checkpointed thread,
            retrying by RESUMING (not restarting) on a retryable failure
            -> LangGraph supervisor (langgraph-supervisor, PostgresSaver checkpointer, thread_id = session_id)
                 -> accounts_agent / transaction_agent / service_agent (create_agent() per domain)
                      -> accounts_tools.py / transactions_tools.py / service_tools.py (StructuredTool wrappers)
                           -> tool_utils.idempotent() guards create_account/create_transaction/create_service_request
  -> /accounts, /accounts/{id}/transactions, /transactions/{id},        [deterministic REST, no LLM,
     /accounts/{id}/service-requests, /service-requests/{id}            real 404/400/409/422]
       -> accounts_router.py / transactions_router.py / service_router.py
            -> global exception handlers map exceptions.py -> HTTP status + {detail, error_type}
                                     |
                                     v  (both paths converge here)
                      accounts_server.py / transactions_server.py / service_server.py (UNCHANGED business logic)
                           -> crud_*.py -> database.py / models.py -> Postgres
```

**LLM client:** `openai/gpt-oss-20b` on Groq — `llm.py`, OpenAI-compatible shape (`base_url`+`api_key`), provider went Ollama → DeepSeek → Groq after two "thinking" models broke the actual multi-turn supervisor flow (PROBLEMS.md #10).

**Resolved for the REST surface:** `/chat` was the *only* functional endpoint — every request, including fully deterministic CRUD, had to go through the LLM, and that's also why `/chat` could only ever return `200` (natural-language replies can't carry a reliable status code). Added REST endpoints per domain that call the same business-layer functions directly, no LLM in the loop, with real HTTP status codes (404/400/409/422) via global exception handlers and a machine-readable `error_type` field. `/chat` itself is untouched and still communicates errors conversationally inside `reply` — correct for a chat endpoint, and no longer the *only* option for a caller that needs structured errors.

**Also noticed, not fixed (pre-existing, out of scope):** `delete_account` doesn't check for or cascade related transactions/service_requests — deleting an account leaves orphaned rows referencing a nonexistent `account_id`.

**Correctness fix from a live demo (PROBLEMS.md #13):** a manual demo request produced a triple deposit — traced to two compounding bugs (retry-restart replaying an already-committed tool call, and the supervisor occasionally re-delegating a completed request to the same sub-agent). Fixed at three layers: checkpoint-based resume (`InMemorySaver` + per-request `thread_id`, resume on retry instead of restart), tightened supervisor/sub-agent prompts (measured: double-delegation dropped from ~1/10 to 0/20 trials), and a deterministic `tool_utils.idempotent()` guard on the three `create_*` tools that rejects a duplicate `(tool, args)` call within the same conversation thread regardless of why the LLM issued it twice — verified directly at the tool layer without needing an LLM call. `tenacity` dependency removed (retry logic is now the manual resume loop in `graph.py`).

**delete_account isolated from agents/chat:** closing an account isn't a customer/agent self-service action — no IAM/elevated-access layer exists yet (Phase 6) to gate it. Removed `delete_account` from `ACCOUNTS_TOOLS` so no sub-agent can reach it via `/chat`; updated `accounts_agent`'s and the supervisor's prompts to say so explicitly rather than let the LLM attempt a workaround. The REST `DELETE /accounts/{id}` endpoint stays in `accounts_router.py` (a future admin caller needs a way in once real access control exists) but is explicitly documented as NOT currently access-controlled — isolating it from the agent path was the fix in scope, locking down who can call it directly is separate, unstarted work. Also noted: no "apply for closure" path exists either (`service_agent`'s request-type allowlist has no closure type) — a real gap, flagged for whoever builds the admin/IAM layer, not built here.

**Routing-accuracy evaluation reclassified:** moved out of "Phase 3 remaining" — a real evaluation (does the LLM route ambiguous/multi-intent input correctly) needs a live-model harness and belongs in Phase 9 (Agent Evaluation Suite, not started), not folded into this phase's exit criteria. In the meantime, all four prompts (`ACCOUNTS_AGENT_PROMPT`/`TRANSACTION_AGENT_PROMPT`/`SERVICE_AGENT_PROMPT`/`SUPERVISOR_PROMPT`) were pulled out to named constants in `graph.py`, with `tests/test_supervisor_prompt.py` asserting on their content (every agent named, anti-re-delegation rule present, clarification fallback present) — zero LLM calls, cheap to run in CI, but only a regression guard on the prompt text, not a verification that the model actually follows it.

**DeepSeek re-evaluated as a Groq fallback, rejected again:** researched current DeepSeek model names (`deepseek-v4-flash` is a retired alias; the live model is `DeepSeek-V4.1-Flash`, served under the model string `deepseek-flash`). A standalone call looked clean (no `reasoning_content` in the response), but testing against the *real* multi-turn supervisor flow — the same methodology that caught this the first time (PROBLEMS.md #10) — reproduced the identical failure: `reasoning_content` must be echoed back on the second turn, which breaks LangGraph's supervisor handoff. Confirms this isn't a one-off from before; the current DeepSeek Flash model still isn't viable for this architecture. Reverted to Groq. Total cost of checking: 2 live calls. Worth revisiting only if DeepSeek ships a non-thinking model variant, or if `langchain_openai.ChatOpenAI` gains native `reasoning_content` pass-back support.

**Not yet done in this phase:** ambient rate-limit handling for Groq's free tier is just `max_tokens=500`, not a real backoff strategy (and Groq's *daily* token cap was hit repeatedly during this session's testing — the free tier is tight enough that any serious further testing needs either a paid tier or very sparing use of live calls).

**Unbounded in-memory state — resolved by Phase 4, not here:** the in-memory checkpointer and idempotency dedup dict growing forever was flagged as a priority item; the actual fix landed as part of building the Session Store (Phase 4, see its own row and PROBLEMS.md #15) rather than as a standalone patch, since a real session lifecycle was needed either way.
