## Current Focus

**Phase 3 — LLM Integration.** Core agentic build complete, verified end-to-end over real HTTP.

**Final shape:**

```
main.py (/chat: ChatRequest{session_id, message} -> ChatResponse{reply})
  -> graph.py: run() -> supervisor.invoke() against a checkpointed thread,
       retrying by RESUMING (not restarting) on a retryable failure
       -> LangGraph supervisor (langgraph-supervisor, InMemorySaver checkpointer)
            -> accounts_agent / transaction_agent / service_agent (create_agent() per domain)
                 -> accounts_tools.py / transactions_tools.py / service_tools.py (StructuredTool wrappers)
                      -> tool_utils.idempotent() guards create_account/create_transaction/create_service_request
                           -> accounts_server.py / transactions_server.py / service_server.py (UNCHANGED business logic)
                                -> crud_*.py -> database.py / models.py -> Postgres
```

**LLM client:** `openai/gpt-oss-20b` on Groq — `llm.py`, OpenAI-compatible shape (`base_url`+`api_key`), provider went Ollama → DeepSeek → Groq after two "thinking" models broke the actual multi-turn supervisor flow (PROBLEMS.md #10).

**Known trade-off, not yet resolved:** the earlier HTTP-status-code work (404/400/422 on `AgentResponse.error`) no longer applies — `/chat` now always returns `200`, and business-rule failures (insufficient funds, invalid status transition, etc.) are communicated by the LLM conversationally inside `reply`, not as a distinct machine-readable error field. This is the expected shape for a chat-style endpoint, but it's a real regression for any caller that wants to branch on *why* something failed without parsing natural language. Revisit if/when a UI needs that.

**Also noticed, not fixed (pre-existing, out of scope):** `delete_account` doesn't check for or cascade related transactions/service_requests — deleting an account leaves orphaned rows referencing a nonexistent `account_id`.

**Correctness fix from a live demo (PROBLEMS.md #13):** a manual demo request produced a triple deposit — traced to two compounding bugs (retry-restart replaying an already-committed tool call, and the supervisor occasionally re-delegating a completed request to the same sub-agent). Fixed at three layers: checkpoint-based resume (`InMemorySaver` + per-request `thread_id`, resume on retry instead of restart), tightened supervisor/sub-agent prompts (measured: double-delegation dropped from ~1/10 to 0/20 trials), and a deterministic `tool_utils.idempotent()` guard on the three `create_*` tools that rejects a duplicate `(tool, args)` call within the same conversation thread regardless of why the LLM issued it twice — verified directly at the tool layer without needing an LLM call. `tenacity` dependency removed (retry logic is now the manual resume loop in `graph.py`).

**Not yet done in this phase:** no evaluation of routing accuracy across ambiguous/multi-intent inputs; ambient rate-limit handling for Groq's free tier is just `max_tokens=500`, not a real backoff strategy (and Groq's *daily* token cap was hit during this session's testing — the free tier is tight enough that any serious further testing needs either a paid tier or very sparing use of live calls); the in-memory checkpointer and the idempotency-guard's dedup dict both grow unbounded for the life of the process — fine for a single-process prototype, would need real TTL/eviction before production.
